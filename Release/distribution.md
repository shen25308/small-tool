# Distributing Shishi for macOS

For direct downloads, evaluate the exact ZIP or DMG offered to users. Record its version, SHA-256 digest, Apple notarization submission ID, and the macOS version on the test machine.

## Local evidence

From this directory, run `python3 verify-release.py`. The default target is the Shishi.app next to the source directory. Pass a different app as the first argument if needed. Use `--artifact` to hash the downloadable package and `--check-staple` to run Apple's `stapler validate`. The script prints JSON. Exit status 0 means all requested checks passed, 1 indicates a failed check, and 2 means the check could not run. It does not access publisher accounts, email accounts, or the user's Keychain.

The 1.2 baseline targeted arm64 and macOS 26. The bundle passed signature-integrity checks, but its executable and ten inference components lacked production Developer ID signatures and its main executable lacked Hardened Runtime. The pinned model hash matched and license files were present. Repeat the checks for each new build.

| Evidence available on the build machine | Evidence needed from a publisher or platform |
| --- | --- |
| Version, architecture, deployment target, signature integrity, signing identities, timestamps | Apple developer account, Developer ID Application certificate and private key, an accepted notarization submission |
| Model hash, bundled licenses, ticket validation | A reachable final download and an installation on a clean Mac with download quarantine intact |
| Simulated OAuth redirects, scopes, error handling, and disconnect | Production OAuth registrations, real account consent, revocation and reconnect, Google verification and tenant approvals where applicable |
| Codex completion receipts and tests of the local Grok delivery command | Supported client versions and a receipt delivered by an actual Grok Bot task after local execution approval |

## Historical preview evidence

The 1.3.1 preview used a real Codex file edit to render a result from its local completion record. Checks covered the independent nonactivating window, input focus and selection in the original editor, expanded replies, older inbox data, and persisted read state. Production registrations and real accounts are still needed to verify consent, renewal, revocation, reconnect, and privacy notices. The [1.3.1 report](checks-1.3.1.json) and [1.3 report](checks-1.3.json) record historical signatures and licenses under the app name that was used at the time. The app bundles Python for macOS ARM64. ## Apple signing and notarization

1. Prepare the production bundle identifier, a Developer ID Application signing identity, and a separate release copy. Keep the private key and notarization credentials in the publisher's Keychain or release system. The normal `build.py` output uses local development signing.
2. Sign the inner libraries, inference engine, Python and helper executables before signing the outer app. Enable Hardened Runtime where required, use secure timestamps, and exclude debugging entitlements. Check each actual component. Changes to the UI, model, or scripts after signing require signing the bundle again. [Apple distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac) · [Notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
3. For ZIP delivery, wrap the signed app with `ditto -c -k --keepParent`, submit it with `xcrun notarytool submit`, wait for Accepted, and save the ID and log. Staple the app, validate the ticket, then create and hash the final ZIP. For DMG delivery, sign, submit, and staple the final outer image. [Notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) · [Distribution packaging](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)
4. Download the final artifact on a clean supported Mac with quarantine intact. Exercise first launch online and offline, moving to Applications, upgrading an existing install, retaining tasks and drafts, avoiding duplicate writers, and reopening. Run an English and a Chinese task extraction with the bundled model. On a Mac without Xcode or Homebrew, test mail and GitHub with the embedded Python and verify the Python requirements of each advertised MCP or Grok entry point. Publish supported hardware, minimum OS, download size, version, digest, support contact, and privacy policy.

## Mail connectors

The implementation uses the system browser, a loopback PKCE callback, Keychain access owned by the main app, scoped token requests from the mail subprocess over an anonymous channel, per-account sender filters, local synchronization, and optional removal of local cards. Both native adapter status requests have run, and simulated replies confirmed that only public account fields reach the UI. Verify authorization, refresh, revocation, and deletion with production registrations and real test accounts.

**Gmail.** The adapter requests `gmail.metadata` for subjects, senders, timestamps, and related metadata. Google lists this as a restricted scope. Configure a production Google Cloud project, enable the Gmail API, create a desktop OAuth client, set the product name, domain, home page, privacy policy and support contact, and follow the applicable restricted-scope review. Prepare a minimal-scope explanation and a consent demonstration. If restricted data passes through or is stored on a server, assess Google's security assessment requirements. Test the actual response fields, offline conditions, revocation, and the initial synchronization boundary. The metadata scope does not support the `q` parameter on `messages.list`. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) · [Restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification) · [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) · [Messages list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list)

**Outlook.** The adapter requests delegated `Mail.ReadBasic`, `User.Read`, and `offline_access` for basic mail properties, identity, and refresh. Register a desktop public client with Entra and check account types and redirects. Basic mail access excludes bodies, previews, and attachments. Organizations can require administrator approval. Verify publisher requirements with target tenants and test consent, denial, renewal, and revocation using personal and supported work accounts. Keep success evidence and minimal error details. [Graph permissions](https://learn.microsoft.com/en-us/graph/permissions-reference#mailreadbasic) · [OAuth and PKCE](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow) · [Publisher verification](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview)

**Data and disconnect.** Explain fields, sync scope, storage, purpose, and retention before connection. Verify in the candidate app that tokens are stored only in the current user's Keychain and do not appear in logs, configuration, cards, or examples. Test account isolation with two accounts. Disconnect one and confirm that future syncing stops and the token is removed. Verify the chosen retention or deletion behavior for existing cards and cursors. Test local data removal and provider-side revocation, then document these results in the public policy with publisher contact details. [Google production policy](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance)

The mail token service uses a dedicated v2 Keychain identifier. Release verification checks that the bundle has no standalone MailVault command-line entry point. Nine isolated Keychain branches have been exercised with test credentials and the bundled Python, including connection writes, sync reads and refresh, disconnect deletion, and cross-account denial. Direct requests from an independently launched bridge script were denied. Repeat these checks when signing or process layout changes and complete a separate real OAuth test. Users of preview builds that stored live tokens under the old v1 service should revoke the old provider authorization before reconnecting.

## Client compatibility and third-party components

- Mail and GitHub use the bundled CPython 3.12.14 interpreter. Verify the launcher, interpreter, standard library, upstream license inventory, CPython and OpenSSL notices, and upstream archive hash. Sign all shipped Mach-O executables and extensions. Have the interpreter load SSL, make an HTTPS request with a test account, validate the TLS peer, and exercise Keychain access.
- Automatic Codex receipt collection depends on local session fields. For each supported version, complete a real main-conversation task; check the thread, text, deduplication, unread state, and catch-up after restart. Include interrupted turns and internal child tasks. Record the client version and date.
- The Grok desktop task executes a local delivery command with approval managed by Grok. Verify a delivery from a real Grok Bot task before advertising support. The Grok Build stop hook and generic MCP tool require separate tests. [Grok local execution approvals](https://docs.x.ai/grok-bot/approvals-security-and-privacy)
- The bundled model is Qwen2.5-1.5B-Instruct-GGUF Q4_K_M. Native inference uses llama.cpp b12224. Distribute the full Apache-2.0 and MIT notices with the components, versions and source references. Update the inventory, hashes, and sizes when replacing dependencies. The model is approximately 1.12 GB; measure the actual compressed download for the release. [Qwen model and license](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF) · [llama.cpp license](https://github.com/ggml-org/llama.cpp/blob/b12224/LICENSE)

Retain the final URL and hash, accepted notarization record and ticket validation, clean-Mac installation evidence, checks for each advertised connector, and published privacy notice.
